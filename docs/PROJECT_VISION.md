## 一、产品定位

### 一句话定义

> **个人幸运生成器** —— 用你的星座、幸运数字、梦境等个人信息，生成属于你自己的号码。

### 重要：定位调整（用户决策时确定过）

~~彩票选号工具~~ → ✅ **个人幸运生成器**

**为什么调整？**
- "彩票"二字在国内/海外都有政策敏感
- "个人幸运生成器"听起来更有趣味、范围更广
- 不仅限于彩票，还可用于：决策辅助、抽签、许愿、娱乐

### 中文副标题
> 用你的星座、幸运数字、梦境，生成属于你的幸运号码

### 英文副标题
> Generate your lucky numbers from your zodiac, dreams, and personal factors

## 二、核心价值主张（产品灵魂）

> **让用户感觉"我参与了决策"，而不是"系统给我一个号码"。**

### 心理学基础
**Illusion of Control（控制错觉）** — 博彩心理学经典研究：
- 用户越觉得"自己参与了"，越倾向于继续使用
- 自选号码的人比机选的人**复购率高 40%+**
- 这是**已被验证的认知偏差**，不是玄学

**所以这个产品本质上是**：合理利用认知偏差，给用户更好的心理体验。

## 三、双线策略（用户决策时确定）

**国内 + 国外 并排走，底层技术共用，本地化分开做**。

### 国内策略

- **市场**：熟悉国内彩票市场（双色球、大乐透等）
- **收费**：暂不收费，做免费版本
- **原因**：国内用户对收费敏感，免费版本更容易推广
- **政策要点**：严格遵守合规边界（详见第六节）

### 国外策略

- **市场**：英文为主，逐步扩展
- **收费**：长期走 Freemium + 订阅模式
- **优势**：海外付费习惯成熟、政策相对宽松
- **挑战**：用户英文一般，需请专业人士润色关键文案

### 双线共享部分

- 底层算法（因素 → 号码映射）
- UI 组件库
- 状态管理
- 本地存储
- PWA 基础设施
- i18n 框架

### 双线差异部分

- 默认语言、彩种、文案
- 合规文案（不同国家不同法规）
- 支付集成（国内 vs Stripe）
- 推广渠道

## 四、技术选型（已确定）

### 形态：**Progressive Web App (PWA)**

**为什么选 PWA？**

| 优势 | 这个产品场景的契合 |
|------|------------------|
| 跨平台一套代码 | 国内 + 国外不需要分别开发 |
| 添加到主屏像 App | 提升用户体验 |
| 离线可用 | 地铁、电梯、信号差的场景 |
| 一秒启动 | 适合"碎片化、即时性"使用 |
| 不需应用商店审核 | 快速迭代，无需 3-7 天审核 |
| 体积小（1-3 MB） | 比原生 App 30-80 MB 小得多 |
| URL 分享 | 朋友推荐一个链接就行 |

### 技术栈

- **前端**：HTML + CSS + 原生 JavaScript（或轻量 Vue/Svelte）
  - 暂不引入 React（对这个产品来说太重）
- **Service Worker**：实现离线缓存
- **Web App Manifest**：配置图标、名称、启动画面
- **localStorage / IndexedDB**：本地存储用户因素、历史
- **i18n**：中英双语支持
- **托管**：GitHub Pages（免费、自动部署）

### 不需要的东西（暂）

- ❌ 后端服务器
- ❌ 数据库
- ❌ 用户账号系统（用本地存储足够）
- ❌ 任何重型框架

## 六、合规边界（重要！）

### 🟢 可以做（核心业务）

- ✅ 提供生成号码的工具
- ✅ 用户输入自己的玄学因素
- ✅ 保存历史记录、做统计图表
- ✅ "运势解读"作为娱乐内容（明确标注"仅供娱乐"）

### 🟡 灰色地带（可以做但要小心）

- ⚠️ 卖"高级运势解读""专家策略"等玄学内容
  - 必须标注"娱乐参考"
  - 避免承诺中奖
- ⚠️ 接入广告 → 注意《个人信息保护法》
- ⚠️ 推荐用户去特定彩票平台购买（"导流"，规模大了有风险）

### 🔴 不能碰（一旦碰了产品会死）

- ❌ 直接卖彩票、代购、合买
- ❌ 声称"提高中奖率""保证中奖"
- ❌ 声称"内部数据""破解算法"
- ❌ "专家预测"并收费（算命+收费双重风险）

### 必须写进产品的免责文案

```
本应用仅供个人娱乐，所生成的号码不保证任何中奖概率。
彩票是随机的，请理性对待，量力而行。
未成年人禁止使用。
```

> **这几句话非常重要**——既是合规护身符，也是产品态度。

## A.2 原项目的价值（要保留的部分）

### 算法引擎（**这是真正的资产**）

```js
const SCHEMES = {
  A: { name: '重热度', a: 4, b: 1, c: 1, d: 1 },
  B: { name: '重偏好', a: 1, b: 4, c: 1, d: 1 },
  C: { name: '重环境', a: 1, b: 1, c: 4, d: 1 },

权重公式：
```
权重 = a * 历史热度 + b * 是否用户偏好 + c * 是否环境数字 + d * 随机

支持大乐透（5+2）、七星彩（7 位），含完整的奖级判定（7 级）。

## A.6 lucky-pick 的算法扩展

原算法只支持"幸运数字/排除数字"作为用户输入。**扩展后**：

```js
// 用户因素库（可堆叠）
const factors = [
  { type: 'lucky_numbers', data: [7, 18], weight: 0.8 },
  { type: 'birthday',     data: '1990-05-20', weight: 0.5 },
  { type: 'zodiac',       data: 'taurus',  weight: 0.6 },
  { type: 'dream',        data: ['水', '鱼'], weight: 0.4 },
  { type: 'avoid',        data: [13], weight: 1.0 },  // 排除永远是 1.0
];

// 算法（每个号码的"被选概率"）
权重 = a * 历史热度
     + Σ(因素i.weight * 因素i.包含(n) ? 1 : 0)
     + c * 环境数字加成
     + d * 随机
     - if (avoid.has(n)) w *= 0.05  // 排除数字大幅降权
```

这个扩展**保持原算法的简洁性**，只是让"用户偏好"这一层变得更丰富。
